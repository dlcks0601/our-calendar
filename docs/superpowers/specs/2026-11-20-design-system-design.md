# our calendar 디자인 시스템 — 설계

- 작성: 2026-11-20
- 상태: 승인됨 (2026-11-20)

## 왜 하는가

화면은 완성돼 있지만 값이 흩어져 있다. 같은 검정 주 버튼이 클래스 조합 12종으로 쓰이고,
글자 크기는 10.5px, 11.5px 같은 값을 포함해 18종이다. 색 하나를 바꾸려면 여러 파일을 고쳐야 하고,
새 화면을 만들 때 기준이 없다. 값과 변형을 한 곳에서 정의하고 화면은 그것을 고르기만 하게 만든다.

당근의 SEED Design에서 구조와 원칙을 가져온다. 값과 이름은 이 제품의 것으로 둔다.

## 목표

- 토큰과 컴포넌트 변형의 원천을 한 곳에 둔다. CSS 변수와 타입은 거기서 생성한다.
- 화면 코드에서 임의값(직접 쓴 색, 임의 글자 크기)을 없앤다.
- 버튼, 칩, 배지, 선택 행 같은 반복 요소를 컴포넌트로 만들고 변형을 고르는 방식으로 쓴다.
- 배포된 사이트의 `/design-system`에서 토큰과 컴포넌트를 볼 수 있다.
- 임의값이 다시 들어오면 테스트가 실패한다.

## 하지 않는 것

- 다크 모드. 토큰 구조는 대비할 수 있게 두되 값은 만들지 않는다.
- 별도 패키지 분리, 모노레포, 헤드리스 컴포넌트 분리.
- YAML 전용 언어와 범용 생성기.
- Figma 연동.
- 화면 구성과 동작의 변경. 이번 작업은 같은 화면을 시스템 위로 옮기는 일이다.

## 실패 조건

- 화면이 의도하지 않게 달라진다. 전후 화면을 픽셀로 대조해 달라진 곳을 전부 확인한다.
- 토큰 이름이 SEED의 복사본이 된다. 구조(역할별 분류)는 가져오되 이 제품의 말로 짓는다.
- 시스템이 화면보다 커진다. 실제로 쓰이는 값과 변형만 정의한다.
- 테스트 347개, 타입 검사, FSD 린터 중 하나라도 깨진다.

## 정한 것

### SEED에서 가져오는 것과 다르게 하는 것

| SEED | our calendar |
| --- | --- |
| Rootage: YAML 명세 → 여러 언어로 생성 | TypeScript 명세 → CSS 변수와 타입 생성. 언어는 하나라 YAML이 필요 없다 |
| 팔레트 → 시맨틱 → 컴포넌트 3계층 토큰 | 같은 3계층. 이름은 이 제품의 역할로 짓는다 |
| qvism 레시피: base · variants · compoundVariants | 같은 모양의 작은 `recipe` 함수를 직접 둔다. Tailwind 클래스를 조합한다 |
| 상태를 의사 클래스와 data 속성으로 함께 표현 | 같은 방식 |
| 생성물은 직접 고치지 않는다 | 같은 규칙. 생성물이 명세와 어긋나면 테스트가 실패한다 |
| 시각 회귀 검사 | 헤드리스 캡처와 픽셀 대조를 스크립트로 둔다 |
| 문서 사이트 | 앱 안의 `/design-system` 화면 하나 |

### 토큰

- **색**: 팔레트(회색 단계, 하늘, 초록, 노랑, 코랄, 스톤, 빨강) → 역할(글자 `fg`, 바탕 `bg`, 선 `stroke`) → 컴포넌트.
  주 행동은 검정이다. 일정 종류 색과 사람 색도 토큰으로 올린다.
- **글자**: 크기와 줄 높이를 묶은 단계. 18종을 단계로 맞추며 0.5~1px 달라지는 곳이 생긴다.
- **간격, 크기, 모서리, 그림자, 모션(시간, 가속, 스프링)**: 실제로 쓰이는 값만 단계로 정리한다.

### 컴포넌트 (`src/shared/ui`)

버튼, 아이콘 버튼, 칩, 배지, 선택 행, 입력 필드, 바텀시트, 토스트, 안내 문구.
이미 있는 칩, 배지, 바텀시트, 날짜·선택 필드는 새 토큰과 조합표 위로 옮긴다.

### 위치 (FSD)

- `src/shared/tokens/spec/` 명세. 문서 화면과 테스트가 같은 명세를 읽어야 해서 앱 코드 안에 둔다
- `src/shared/tokens/__generated__/` 생성된 테마 CSS, `scripts/generate-tokens.ts` 생성 스크립트
- `src/shared/ui/` 컴포넌트와 조합표
- `src/pages/design-system/` 문서 화면, 라우트는 `app/design-system/page.tsx`

### 검증

- 명세의 글자·바탕 조합이 대비 4.5:1 이상인지
- 생성물이 명세와 같은지
- `src`에 직접 쓴 색과 임의 글자 크기가 없는지
- 화면 전후 픽셀 대조
- 기존 테스트 347개, 타입 검사, FSD 린터, 빌드

## 구현 결과와 다른 점 (2026-11-20 추가)

승인된 본문은 고치지 않는다. 구현과 최종 검토를 거치며 본문과 달라진 것을 여기에 적는다.

### 수치

본문의 "지금 상태" 표는 처음 잰 값이다. 측정 스크립트를 저장소에 넣고(`scripts/measure-design-values.mjs`) 같은 트리를 다시 잰 결과는
모서리가 12종(본문은 13종. 방향 접두사 `rounded-t`를 값 한 종으로 세던 것을 바로잡았다)이고 나머지 항목은 본문과 같다.
이후 수치는 README의 "전후 수치" 절에 있다.

### 컴포넌트

본문의 아홉 가지 중 버튼, 아이콘 버튼, 칩, 배지, 선택 행 다섯을 만들었다.

- 입력 필드, 토스트, 안내 문구는 만들지 않았다. 입력은 두 곳의 모양이 서로 다르고 나머지는 쓰는 곳이 하나씩이라,
  만들면 본문의 실패 조건("시스템이 화면보다 커진다")에 걸린다.
- 바텀시트와 날짜·선택 필드는 토큰만 옮겼고 조합표는 쓰지 않는다.
- 직접 쓴 `button` 요소는 55곳에서 32곳이 됐다(그중 4곳은 컴포넌트 자신의 구현). 날짜 칸, 일정 블록처럼 모양이 한 곳에만 있는 것은 남겼다.
- `ghost` 변형은 정의만 있고 화면에서 쓰지 않는다. 옮길 후보였던 글자 버튼 두 곳과 닫기 버튼은 글자 색과 크기가 변형과 달라,
  화면을 바꾸지 않으려고 그대로 두었다.

### 대비

본문은 "명세의 글자·바탕 조합이 대비 4.5:1 이상"을 검증 항목으로 적었다. 구현은 이 기준을 전부 지키지 못한다.

- 본문 글자(강조, 본문, 검정 면 위 글자, 경고, 일정 제목)는 4.5:1 이상이다.
- 보조 글자는 이 제품의 기준을 3:1로 두었다. 흰 바탕 3.36:1, 옅은 바탕 3.06:1로, 작은 글자에 4.5:1을 요구하는 WCAG AA에는 못 미친다.
- 옅은 안내 글자는 1.98:1로 3:1에도 못 미친다. 대비표에 미달로 적는다.
- 값을 고치지 않은 이유: 이번 작업의 조건이 화면을 바꾸지 않는 것이고, 회색을 어둡게 하는 것은 화면 전체의 인상을 바꾸는 디자인 결정이다.
- 일정 블록의 시간 글자 네 색은 3:1에 못 미쳐 어둡게 조정했다. 본문의 "화면 구성과 동작의 변경을 하지 않는다"와 다른 결정이다.

### 화면이 달라진 정도

본문의 실패 조건은 "화면이 의도하지 않게 달라진다"이다. 이전 빌드와 최종 빌드를 엄격한 기준(허용치 0.02, 가장자리 픽셀 포함)으로
대조한 결과 18장 중 16장이 2.6% 이하이고, 일정 만들기 모바일 3.57%, 완료 모바일 14.68%가 그보다 크다.
완료 화면은 배경의 번진 색을 팔레트의 가장 가까운 단계로 옮겨 조금 옅어진 것이다(채널당 평균 5, 최대 12).
원래 값을 그대로 두려면 팔레트에 단계를 더해야 해서, 가까운 단계를 쓰는 쪽을 골랐다.
열린 시트·팝오버, 호버 상태, 스캔 화면은 대조하지 못했다.

### 토큰 이름

본문의 실패 조건은 "토큰 이름이 SEED의 복사본이 된다"이다. 분류(palette → fg · bg · stroke)와 단계에 번호를 붙이는 방식(`r1`…, `s1`…),
`-pressed` · `-weak` 꼬리말은 SEED와 같다. 역할 이름(`strong`, `default`, `ink`, `page` …)과 값은 다르다.
SEED 저장소의 `packages/rootage`(radius, shadow, color)와 직접 대조해 확인했다.

### 그 밖에

- 스프링 프리셋은 넷이다(자리 이동, 튀어나옴, 팝오버, 바닥 시트). 바닥 시트는 넘치지 않아야 해서 따로 두었다.
- 무채색은 역할 이름으로만 쓰도록 테스트로 강제한다. 색 계열은 색이 곧 정보인 곳에서 팔레트 단계를 직접 쓴다.
- 임의값 검사는 정규식이 아니라 Tailwind로 실제 컴파일하는 방식이다. 테마에 없어 아무 스타일도 내지 않는 클래스까지 잡는다.
